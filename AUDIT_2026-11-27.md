## Устройство проекта

Работодатель регистрируется, проходит модерацию и создаёт заявку. Работники получают вакансии и откликаются; администратор подтверждает состав, ведёт предоплату, начало и завершение смены, закрывает расчёт. Бот и веб-панель используют общие модели и тексты, но отдельные реализации переходов. Есть напоминания, отметки явки, штрафные баллы, документы, рефералы и города.

Сильные стороны: выделенные сервисы, изолированные тесты с FakeSession, проверка владельца в ряде callback-обработчиков, CSRF на POST в админке, экранирование многих пользовательских текстов, журнал действий. Наличие тестов не покрывает все сценарии ниже.

## Подтверждённые по коду проблемы

### 1. Высокий приоритет: потеря напоминаний при ошибке Telegram

`bot/utils/scheduler.py:77–79`, аналогично другие ветви: сначала `L.add_event` записывает и коммитит событие, затем вызывается отправка. `bot/utils/lifecycle.py:36–44` при ошибке возвращает False. Следующий проход увидит событие и больше не попробует доставить напоминание. Временный сбой может лишить работника адреса и напоминания о смене.

Исправление: очередь доставки с состояниями pending/sent, повторами и контролем результата. Простая перестановка отправки и записи уменьшает потери, но оставляет риск дублей при сбое между ними.

### 2. Высокий приоритет: веб-панель подтверждает работника после завершения смены

`admin/services.py:176–194` запрещает подтверждение только для payment_completed/cancelled. Поэтому ожидающий отклик можно подтвердить при shift_completed, если мест хватает. Заказ уже завершён, новый работник остаётся confirmed и получает приглашение на завершённую смену. В боте `bot/utils/lifecycle.py:275` список разрешённых статусов уже ограничен набором и предоплатой.

Исправление: одинаковый явный список допустимых статусов и тест проверки через веб-панель.

### 3. Средний приоритет: неверное среднее по отдельным критериям рейтинга

`services/worker_service.py:83–102`: для punctuality/responsibility/quality/communication знаменателем служит общее число отзывов, хотя поля необязательные. После отзыва без punctuality первый отзыв с punctuality=5 может дать 2.5. `admin/services.py:397–405` считает среднее по заполненным значениям, поэтому перерасчёт из панели способен изменить оценку без новых отзывов.

Исправление: агрегировать каждый критерий по его непустым видимым значениям; единый способ расчёта для бота и панели.

### 4. Средний приоритет: TIMEZONE не управляет временем смен

По поиску в Python-коде TIMEZONE встречается только в объявлении `config/settings.py:64`. Обработчики и планировщик сравнивают shift_date с `datetime.now()`, служебные даты записываются через `datetime.utcnow()`. При запуске на сервере с другой временной зоной начало смены, поздние отказы и напоминания будут интерпретироваться по часовому поясу сервера.

Исправление: договориться о хранении времени, использовать UTC и явное преобразование Europe/Moscow при вводе и показе. Существующие даты требуют отдельного плана переноса.

## Риски, требующие отдельного воспроизведения

- `ResponseService.create_response` делает SELECT, затем INSERT; в прочитанной модели Response нет уникальности `(order_id, worker_id)`. Одновременные нажатия могут создать дубли; последующий scalar_one_or_none перестанет работать. Нужны ограничение БД и обработка конфликта, с проверкой существующих дублей перед миграцией.
- Подтверждение места делает проверку количества и изменение без видимой блокировки заказа. Одновременные действия из бота и панели требуют теста конкурентного доступа, особенно на PostgreSQL.
- `set_status_manual` меняет статус без полного выполнения побочных действий перехода. Возврат заказа назад и повторное завершение требуют проверки на повторное начисление completed_shifts.
- MemoryStorage теряет незавершённые анкеты после рестарта.
- Настройки по умолчанию допускают стандартные пароль/SECRET_KEY и слушают 0.0.0.0. Фактические значения .env не проверялись; это риск конфигурации, не подтверждение открытого доступа.
- `upgrade_schema` добавляет колонки без переноса Python-default в существующие строки и не является полноценной версионированной миграцией ограничений/индексов. Нужны тесты обновления старых баз.
